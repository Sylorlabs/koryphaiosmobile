## Critical journeys

**A. First successful control:** fresh app → unpaired guidance → pair/link → verify host identity → create/select chat/project → choose model → send → stream → stop → compare host result. Phone and desktop must agree on chat/project/output/status.

**B. Keep working:** start delayed preflight → edit/add file → switch chat/host → resolve old preview/consent → no stale send. Submit → type next draft → lose/reject response → retain both drafts. Inspect original chat before manual resend.

**C. Recovery:** stream → background/inactive/active → lock/unlock → interrupt/restore network → restart host. Restore current snapshot/subscriptions exactly once. Repeat with pending attention and accepted-but-unreconciled mutation.

**D. Continuity:** type draft with file → rotate/open keyboard → resize/split tablet → model/controls and back. Preserve draft, focus and reachable actions. Establish the requested Duo target before defining any additional display-transition tests; no official device behavior is currently evidenced.

**E. Full control:** inspect/manage agents, answer attention, browse context/files, safely edit a setting, inspect process/Git/task state and verify host result. Test permission failures and explain restrictions without expanding authority.

## Operating board: how we audit and fix continuously

Every finding gets a permanent ID, severity, route/capability, actual device/build, observed behavior, reproduction steps, affected host/transport, evidence path, owner/next action, and two distinct closure marks: **automated check** and **native journey**. An issue is not closed merely because a patch compiled or a screenshot looked correct. The log lives in [mobile-readiness.md](mobile-readiness.md) and the per-device evidence in [device-matrix.md](device-matrix.md).

**One ticket, one loop:** reproduce → identify host/command ownership → make a bounded fix → run focused test → run available full checks → install the current native build → replay success and failure on the exact device/connection → capture screenshot/trace → update the board → move to the next highest-severity issue. If a required check cannot execute, record the exact blocker and continue another independent ticket. Do not use old binaries as evidence for new JavaScript behavior.

| Priority | Definition | Response |
| --- | --- | --- |
| P0 / stop-ship | Wrong machine/chat, lost or duplicated work, unauthorized remote action, invalid grant, critical crash, unrecoverable streaming. | Fix immediately; add race/contract coverage and native replay before moving to release work. |
| P1 / required | Core action broken/confusing, blank navigation, unreachable controls, invalid reconnection, accessibility blocker, unsupportable major device class. | Fix during active audit; require native replay before TestFlight. |
| P2 / polish | Visual density, excessive taps, motion stutter, recoverable layout/wording issues. | Batch after correctness; preserve design language and test reduced motion/text scaling. |
| P3 / deferred | Minor cosmetic refinement with a documented workaround. | Defer only by explicit release exception with a named reason. |
